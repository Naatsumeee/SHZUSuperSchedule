## 新增「查询」页（分支 `教务查询接入`）

### 需求

在现有三个主页面之外再加一个页面，**排在周视图之后**，提供三个查询入口：

| 入口 | 教务菜单路径 |
|------|--------------|
| 考试安排 | 考试报名 → 我的考试 → 考试安排查询 |
| 课程成绩 | 学籍成绩 → 我的成绩 → 课程成绩查询 |
| 等级考试成绩 | 学籍成绩 → 我的成绩 → 等级考试成绩 |

教务地址 `jwgl.shzu.edu.cn`。要求与现有页面的导航、样式保持一致。

### 关键设计决策

**1. 数据获取走 WebView 抓 HTML，而不是后端 POST**

现有的「刷新可读学期」是后端静默抓取（Cookie + HttpURLConnection）。
但这次不能照搬，原因两条：
- 三类查询的**接口名与参数各校不同**，写死容易失效；
- **考试安排查询需要用户在页面里自选学年学期**，表单参数无法预先确定。

走 WebView 的好处：无论教务怎么改，只要能看见表格就能抓。

**2. 不做逐字段建模，只做「通用表格解析」**

三个页面的表结构完全不同，学校升级一次就可能全变。
所以 `JwglQueryParser` 只做一件事：把页面上的结果表读成「表头 + 行」。
找表优先级：`#dataList` / `#tabList` / `.tbllist` 等常见 id → 兜底取**数据行最多**的表。
只要教务还在用表格展示数据，改版也不会解析失败。

**3. URL 是「候选」而不是「唯一」**

教务各校查询路径差异大，`QueryKind.paths` 存候选列表，只取第一个当「直达」按钮的目标。
UI 上明确写着菜单路径，**打不开就让用户在网页里手动点菜单**，抓取逻辑完全不依赖具体地址。
这样即使我猜的 URL 全错，功能依然可用。

### 踩到的坑

- **`SubPageTopBar` 原本是 SettingsPage 的 `private`**，查询页要用同一套，
  已提升为 `PageHeader.kt` 里的 `internal` 公共组件。
- **加 tab 会让索引整体后移**：`selectedTab` 由 0/1/2 变成 0/1/2/3，
  `MainScaffold` 的 `when (selectedTab)` 和 `BlurredBottomBar` 的 `NavigationBarItem`
  必须同步改，漏一处就串页。
- 查询结果用**覆盖层**呈现而不是替换 WebView —— 换掉会让 AndroidView 被移出组合导致
  WebView 销毁、页面状态丢失。覆盖层方案下 WebView 始终在底层活着。
- WebView 的加载进度要**显式回调出来**（`onProgressChanged`），
  否则进度条永远不动（我第一版就漏了这个）。

### 🔴 发现并修复：WebView 吃掉系统返回键

**现象**：进入查询二级页后按系统返回**毫无反应**（一直停在二级页）。

**根因**：WebView 属于 **View 层级**，会抢在 Activity 的返回分发之前拿到 BACK 事件；
网页一旦有历史记录（CAS 跳转就会产生），返回键就被 WebView 用于「网页后退」并消费掉，
**页面栈永远退不出去，而用户看不到任何变化，像卡死**。

**修复**（`buildQueryWebView` 里加 `setOnKeyListener`，按浏览器惯例）：
- WebView 能后退 → 先 `goBack()` 做网页后退
- 退无可退 → `(ctx as ComponentActivity).onBackPressedDispatcher.onBackPressed()`
  交回 Compose 的 `BackHandler`，由 `PageHost` pop 页面栈

**验证**：连按 3 次返回 → 逐级退出，最终回到系统桌面。✅

> ⚠️ **这条经验对任何「Compose + AndroidView(WebView)」的页面都适用**，
> 导入课表页（ImportPage）没有二级返回需求所以没暴露这个问题。

**根因**：`onCreateWindow` 里把**当前 WebView** 直接赋给 `WebViewTransport.webView`，

（效果 = 新窗口的链接在当前窗口打开）。`ImportPage` 与 `QueryPage` 两处都改。

## 第三轮：🔴 真相 —— URL 没错，是登录检测失效

### 用户提供的关键信息

> 教务系统点击切换不同查询页面时**网址并不会改变**，所有内容均在
> `https://jwgl.shzu.edu.cn/jsxsd/framework/xsMain.htmlx#` 进行查询。

⇒ 确认教务是 **iframe 框架式布局**：主框架地址固定，点菜单只换内部 iframe 的子页。
**用户根本看不到子页地址**，我之前让他"看地址栏拿 URL"的要求是错的。

### 我用 curl 直接实测教务（关键一步）

```
GET /jsxsd/kscj/cjcx_query        → 302 → /jsxsd/sso.jsp
GET /jsxsd/framework/xsMain.htmlx → 302 → /jsxsd/sso.jsp
GET /jsxsd/framework/xsMain.jsp   → 302 → /jsxsd/sso.jsp
```

**全是 302（需要登录），不是 404！**

而 `sso.jsp` 本身返回 **HTTP 200**，内容只有一段 JS 跳转：

```html
<script languge='javascript'>
  window.location.href='http://authserver.shzu.edu.cn/authserver/login?service=...'
</script>
```

**既没有 `<title>` 也没有表单。**

### 🔴 结论：两个此前都判断错了

1. **三条查询路径其实是对的** —— 返回的是「需要登录」而不是 404。
   我当时按强智通用规则猜的路径碰对了。
2. **抓取失败的真正原因是登录态失效**，而 `looksLikeLogin` 认不出 sso.jsp
   （它只看 title 和登录表单），于是把请求归为「找不到查询页」，
   **让我把矛头错指向 URL，白折腾一轮**。

> 教训：**"请求成功但内容不对"时，先把响应体打出来看**。
> 这里 `HttpURLConnection` 跟随重定向拿到了 200 的 sso.jsp，
> 状态码层面完全正常，只看 code 永远发现不了问题。

### 本轮修复

- `looksLikeLogin(resp)` 改三重判据：**最终地址**含 sso.jsp/authserver、
  响应体含 `authserver` 特征串、以及传统登录表单。
- `Resp` 增加 `finalUrl`（`conn.url`，跟随重定向后的地址）。
- `Summary.authFail`：登录失效单独计数，提示语直接说
  「教务登录已失效，请到「设置 → 重新导入课表」登录一次后重试」。
- **手动抓取收集「当前页 + 所有 iframe 子页」的 HTML**
  （`COLLECT_HTML_JS`）：框架布局下只抓 `documentElement.outerHTML`
  得到的是不含子文档的空壳，必然解析不到表格。
- 新增**后台探测** `discover()`：拉主框架页（htmlx 优先，jsp 兜底），
  把菜单里所有 `.do`/`.htmlx` 地址捞出来（含**内联 JS 字符串里的路径**，
  强智菜单多半是 JS 拼的），逐个 GET、按标题归类，全程写日志。
  未登录立即中止（否则白刷几十个请求）。
- `MAIN_FRAME_URL` 改为 `xsMain.htmlx`，保留 `.jsp` 作 `MAIN_FRAME_URL_LEGACY`。

### 走过的弯路：CAS 密码加密

试着用 curl 模拟登录，发现密码不是明文提交：

```javascript
function encryptAES(n, f) { return f ? getAesString(randomString(64) + n, f, randomString(16)) : n }
function encryptPassword(n, f) { try { return encryptAES(n, f) } catch(c) {} return n }
```

即 **AES-CBC/PKCS7**，明文 = `randomString(64) + 密码`，key = 页面给的 salt，iv 随机。
逆向成本高且要处理真实凭据，**果断放弃**，改用「在设备 WebView 里登录」。

### 设备与验证的坑（重要）
- 会话中**设备被换过**：先是 `b18b0725`，后来是 `e87a3fe4`（2410DPN6CC，1440x3200）。
  一度因此误判「存档被清空 / 跑的是旧代码」——其实是在看另一台设备（旧版 + 没登录）。
  **结论：看日志前先 `adb devices` 确认序列号，别把两台设备的现象混在一起推理。**
- **MIUI 下 `adb install -r` 不一定会立刻替换 APK**。核对方法：
  `pm path` 拿到的 base.apk 大小必须与本地 `app-release.apk` 完全一致
  （本次 14,992,995）。大小不一致就是没换上。
- 旧版那种「一个接一个猛发请求」会把教务会话**直接踢掉**
  （实测：第 1 个请求正常，第 2 个起全部 164 字节）。
  `STEP_DELAY_MS = 1200` 不能省。
- 日志排查要先把缓冲区调大：`adb logcat -G 16M`。
  默认 2 MiB 会被系统噪声（qdgralloc 等）冲掉，看起来像「什么都没发生」。

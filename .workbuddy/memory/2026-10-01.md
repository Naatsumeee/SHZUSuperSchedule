# 2026-10-01 工作日志：定位并修复「导入课表后一开就闪退」

## 起因
用户报：软件导入课表后无法启动，开启即闪退；清除数据后可正常进导入页，
但导入后即闪退。

## 🔑 先证伪了一条最可能的怀疑
用户以为与本轮（09-25）的改动有关。**核对后排除**：
- 设备上装的包 md5 = `4de4faf3542d646c1ddc18c788cb9148`，正是记忆里记的 **v166 正式包**；
- 从设备 pull 下来解 dex，**不含** `Logger`/`LogcatLogger`（本轮新增的符号）→ 确认是旧包；
- `lastUpdateTime = 2026-09-29 18:46`，但两份工作副本都停在 09-25 及更早
  → 那个包来自**别处的构建**，与本仓库当前代码无关。

**教训**：用户描述现象时会带上时间联想（「突然出现了」），但**设备上的实际产物**
才是判据。先确认"跑的是哪份代码"，能省掉大量无效排查。

## 排查过程（三层递进）

### 1. 抓不到栈 —— 三个坑叠在一起
- `FATAL EXCEPTION` 全程未出现，`AppLog` 的崩溃钩子也**没有落盘崩溃记录**
  （日志在崩溃点直接断掉）；
- release 包 `run-as: package not debuggable`，`adb root` 不可用（production build），
  `/data/data/.../files` 拒绝访问 → **拿不到任何 App 侧日志**；
- MIUI 的 crashpad 把 logcat 刷满二进制噪声，`grep FATAL` 一无所获。

**破法**：装 **debug 包**（applicationId 相同、签名不同 → 必须先卸载 release，
数据会丢）。装完 `run-as` 立刻可用，`app.log` 能读。

### 2. 拿到关键线索：崩在哪个线程
`logcat` 里捞到：
```
Fatal signal 5 (SIGTRAP), code 1 (TRAP_BRKPT), fault addr 0x... in tid 13377 (RenderThread)
>>> com.shzu.superschedule <<<
AppFaultSentinel: isStartupCrash: true, versionName: BETA-v1.4
```
**崩在 RenderThread** → 一句话排除全部业务逻辑（解析/存档/网络都没问题），
锁定到**渲染/绘制**代码。项目里最复杂的绘制就是 `BlurBar.kt` 的底栏多层模糊。

### 3. 对照实验二分定位
用项目自带的 `bar_diag.txt` 诊断开关（写
`/sdcard/Android/data/com.shzu.superschedule/files/bar_diag.txt`，
**必须 `chmod 666`**，否则 App 读不到）：

| 配置 | 结果 |
|---|---|
| dbg=1（不模糊） | 5/5 存活 |
| dbg=3（`Modifier.blur` 单层） | 存活 |
| dbg=4（裸 `RenderEffect` 单层） | 存活 |
| dbg=0 + 5 层（原默认） | **5/5 崩溃** |
| dbg=0 + 4 层 | ✗ 崩溃 |
| dbg=0 + 3 层 | 5/5 存活 |
| dbg=0 + 2 层 | 存活 |
| dbg=0 + 5 层 + 半径 8dp | ✗ 崩溃（对比 44dp 也崩）|

→ **根因：渐变模糊的层数**。每层都要 `CompositingStrategy.Offscreen` 独立渲染目标，
叠 4 层及以上让 RenderThread 原生崩溃。与半径无关。

### ⚠️ 一个差点导致误判的坑
对照实验必须 **`am force-stop` 之后再 `am start`**。
我中途有一次只 `am start`，进程还在（复用）→ 报「存活」，
差点得出「模糊不是根因」的错误结论。**冷启动才算数。**

## 为什么"清数据后能开"
空数据时 App 停在**导入页**，没有底栏 → 没有这层模糊 → 不崩。
导入后进主页、底栏出现 → 崩。所以这个 bug 的表象「清数据能开、导入后闪退」
**完全不指向数据本身**，是纯粹的视觉巧合。我一开始确实去查了
`ScheduleStore.load` / `QueryStore.sanitize`，属于被表象带偏。

## 修复
- `BAND_COUNT`：5 → **3**（附完整实测表格与崩溃现象的注释）；
- `tuning.bands.coerceIn(2, BAND_COUNT)`：上限由 `8` **卡死到 3**
  —— 否则 `bar_diag.txt` 里写个 5 就能把用户崩回闪退；
- `rememberBarTuning` 的 KDoc 补上「一开就闪退时优先怀疑这里」的排查手法。

## 验证
- debug 包默认配置（bands=3, dbg=0）：**5/5 冷启动存活**，且日志确认
  3 层模糊**真的在绘制**（半径 165/103/41 px 自下而上递减），不是降级成纯色；
- release 包（v171）装回设备：空数据态 3/3 存活；
- **模糊效果经用户真机确认存在** —— 视觉验收通过，没有为了稳定牺牲效果。

## 遗留
- release 包需用户**重新导入一次课表**做最终确认（崩溃只在有数据时复现）；
- 该 bug 自 HyperOS 4.0 / Android 17 升级后出现（设备 `ro.build.version.release=17`，
  `V816`）。推断是系统渲染管线对叠层离屏缓冲的限制收紧所致，
  但**未做跨系统版本对比**，若别的设备也复现请一并回报。
- 本轮为定位装了 debug 包，用户设备上的**原有数据已丢失**（未做备份，
  `adb backup` 需手机端确认、当时未完成）。

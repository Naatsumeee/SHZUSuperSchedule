## 故障现象

**导入课表后 App 一启动就闪退。**

- 卸载 / 清除数据后可正常打开，停在导入页；
- 一旦导入课表、进入主页（底栏出现），**此后再打开必闪退**；
- 异常发生在**极早期**（进程存活约 0.5–1.1 秒），
  MIUI 报 `AppFaultSentinel: isStartupCrash: true`。

## 根因：底栏模糊的叠层数超过渲染管线上限

崩在 **原生渲染线程**，Java 层完全没有异常：

```
Fatal signal 5 (SIGTRAP), code 1 (TRAP_BRKPT), fault addr 0x... in tid ... (RenderThread)
>>> com.shzu.superschedule <<<
```

底栏的「渐变磨砂」是把同一份内容切成多层、每层用不同的模糊半径叠出来的
（自下而上越来越清晰）。**每一层都需要 `CompositingStrategy.Offscreen` 的独立渲染目标**，
叠到 **4 层及以上**就会让 RenderThread 原生崩溃。

实测（HyperOS 4.0 / Android 17，GPU = Adreno）：

| 配置 | 结果 |
|------|------|
| 5 层（旧默认） | **5/5 冷启动崩溃** |
| 4 层 | ✗ 崩溃 |
| **3 层（现值）** | **5/5 存活** |
| 2 层 | 存活 |
| 单层 `Modifier.blur` | 存活 |
| 单层裸 `RenderEffect` | 存活 |
| 5 层 + 半径 8dp（对比 44dp） | **都崩 → 与半径无关，只与层数有关** |

### 为什么「清除数据就能开」

空数据时 App 停在**导入页**，那里**没有底栏**，也就没有这层模糊 → 不崩。
导入后进入主页、底栏出现 → 崩。

所以「清数据能开、导入后闪退」这个现象**完全不指向数据本身**，
纯粹是「导入后才有底栏」的视觉巧合。排查时不要被它引到存档 / 解析逻辑上去。

### 触发条件：系统升级

设备（2410DPN6CC）当前为 **Android 17 / HyperOS 4.0.0.14（V816）**。
推断是系统渲染管线收紧了对叠层离屏缓冲的限制，导致原先可用的 5 层方案越界。
**未做跨系统版本对比**；若其他机型也复现，请一并反馈。

## 修复

`ui/BlurBar.kt`：

1. **`BAND_COUNT` 5 → 3**（附完整实测表格与崩溃现象，避免后人调回去）；
2. **`tuning.bands` 的上限由 `8` 卡死到 `BAND_COUNT`** ——
   原先诊断文件里写 `bands=5` 就能把用户崩回闪退，现在写多大都只会用 3；
3. 补排查注释：**「一开就闪退、且 App 内日志没有崩溃栈」时优先怀疑这里**。

**模糊效果没有牺牲**：真机日志确认 3 层仍在实际绘制
（半径 165 / 103 / 41 px 自下而上递减），不是降级成纯色，磨砂观感经用户确认存在。

## 排查过程留档（供以后遇到同类问题参考）

这个 bug 难在**三个坑叠在一起**：

1. **崩在原生渲染线程** → `FATAL EXCEPTION` 不出现，App 自装的崩溃钩子也抓不到栈，
   日志在崩溃点直接断掉；
2. **只在有数据时崩** → 极易被误导成数据 / 存档问题；
3. release 包不可 `run-as`、设备无 root、`/data` 取不到日志。

有效的打法：

1. 对比**设备上实际安装的包**与本地代码（用 md5 + 解 dex 查新增符号），
   先确认「崩的是哪份代码」——本次据此排除了当天所有改动的嫌疑；
2. 装 **debug 包**（applicationId 相同，需先卸载 release）→ `run-as` 立刻可用；
3. 读 `files/logs/app.log` 确认崩在哪一步；
4. 用 logcat 抓 `Fatal signal` 拿到**崩溃线程名** —— 本例 `RenderThread`
   一句话排除了全部业务逻辑；
5. 用项目自带的诊断开关（`BlurBar` 的 `bar_diag.txt`）做**对照实验**二分定位。

⚠️ 对照实验**必须 `am force-stop` 之后冷启动**：
只 `am start` 会复用已在运行的进程，得出「存活」的假结论（本次差点因此误判）。

# 教务查询三类结果 —— 决策复盘

> 从 `../memory/2026-09-21.md`、`../memory/2026-09-22.md` 中提炼。
> 想知道「为什么查询页是现在这个样子」，看这一篇比翻长日志快。

## 一、为什么不做逐字段建模

三类查询（考试安排 / 课程成绩 / 等级考试成绩）页面结构互不相同，
而且强智各校版式、甚至同校不同模块的表格 id 都不一样
（`dataList` / `tabList` / `tbllist` …），学校升级一次就可能全变。

所以只有一条路：**把页面上的「结果表」找出来，读成「表头 + 行」**。
只要教务还在用表格展示数据，改版也不会解析失败。

代价是**取值只能按表头关键词查**，不能写死列序号 —— 这两件事必须配套，
写死序号就等于把不做建模的好处全扔了。

## 二、三个决定性发现（都来自真机，不是推理）

### 1. `HttpURLConnection` 拿不到会话

后台抓取最初用 `HttpURLConnection` 带上 `CookieManager` 的 Cookie，
返回 **164 字节、无 title 的空壳页**。诊断发现 Cookie 只有 3 项
（`jsxsd` / `SERVERID` / `bzb_njw`），**没有 `JSESSIONID`** ——
教务是多机负载均衡，那两个是负载均衡 Cookie，真正的会话 Cookie 取不到。

改成**在Web­View 里跑 JS `fetch`**（`QueryHtmlFetcher` + 1×1 不可见 WebView），
Cookie / UA / Referer 全由浏览器处理，问题消失。

顺带发现：教务会话极脆，**连续快速请求会被判定爬虫并踢掉会话**
（第 1 个请求正常、第 2 个起全空壳），所以 `STEP_DELAY_MS = 1200` 不是可选项。

### 2. 教务用 `0` 表示「这项没有成绩」

不是留空，是填 0。四六级 0–710、计算机等级 0–100 **不会出现真实的 0 分**，
所以把 0 当空处理是安全的。

这个约定不知道的话，取「分数类成绩」就会挑中占位值 ——
用户反馈的原话是「显示分数需要选择有具体分数的，分数一般不为 0」。

### 3. 等级考试表的第二层表头被写进了 `<tbody>`

这张表 thead 只有一行，父列用 `colspan` 铺开（`1+1+4+3+1+1 = 11` 列），
**真正的子列名（笔试 / 机试 / 总成绩 …）单独占了 tbody 的第一行**。

后果有两个，都是用户实际看到的：

1. 那行前两列是空的，第一个非空单元格就是「笔试」→ 界面凭空多出一条
   **标题为「笔试」、内容全是「机试 / 总成绩」的空卡片**；
2. 4 列「分数类成绩」拿不到子名、全部同名 → 无法分辨哪一列才有分数 →
   只能退化成"取第一个非空值"→ 挑中教务的 `0`。

**关键决策：不是把那一行丢掉，而是把它当第二层表头用。**
只丢不补的话，同名问题依然存在，用户看到的结果**完全没变**。
`repairStrayHeader` 按列号把子名拼到父名后面
（`分数类成绩` + `总成绩` → `分数类成绩 / 总成绩`），再把它从数据里剔除。

判据 `isStrayHeaderRow` 的三条同时满足才算：
非空格 ≥2、**整行一个数字都没有**（真数据行必然带序号/日期/分数）、
且（行内有复读值 或 每个值都能在表头里找到）。

## 三、一个返工：新增"既有剔除又有改造"的函数时，调用点要全接

`repairStrayHeader` 写好以后只接进了 `JwglQueryParser.readTable`（**新抓取**路径），
`QueryStore.sanitize`（**读老存档**路径）还是原先手写的
`filterNot { isStrayHeaderRow(...) }` —— 只剔除、不补名。

现象很隐蔽：构建成功、真机不崩、日志里"移除 1 行"也正常打印，
**只有把表头明细那行日志调出来对着看，才发现 4 列仍然同名**。
所以「老存档不用刷新也能修好」这条承诺其实落空了，多发了一版（v166）。

教训写进了 `PROJECT_PROMPT.md` 第 5 节：**这个函数有两个调用点，改一处必须改两处。**

## 四、看不见用户数据时怎么诊断

release 包 `run-as` 报 `package not debuggable`，`adb root` 也不可用；
换成 debug 包签名不同，覆盖安装会**清掉你要查的那份数据**。

有效办法是让 App 在**读取存档时**自己把「形状 + 表头名」打到 logcat：

- 触发时机必须是**读取**（冷启动就触发），不能是抓取 —— 用户不点刷新就永远看不到；
- **只打表头名，不打单元格值**（个人信息、准考证号都在值里）；
- 走 `android.util.Log`，不占 App 界面上那 800 行业务日志缓冲；
- 单独打一行表头明细：改版后最先失真的就是列名与列数。

这一次正是靠它拿到了三类表的真实列结构，也靠它确认了
「清理逻辑删掉 1 行后，课程成绩 47 行一行没少」——**没有任何误杀**。

## 五、排版为什么按 kind 分派

三类信息重心完全不同，一套通用版式（首字段当标题 + 其余按字段名排）会把重点埋掉：
考试安排里最要紧的是"什么时候、在哪儿考"，课程成绩里最要紧的是"这门课多少分"。

所以 `ui/QueryCards.kt` 按 `QueryKind` 分派三种卡片，
但**取值一律走表头关键词**，与解析器"不做逐字段建模"保持一致。

## 六、排序规则的取舍

用户原话：「筛选考试种类，按照 CET-4、CET-6、NCRE一级、NCRE二级、其他 为顺序排列，
总体以时间顺序排列。」这两句有张力：种类顺序优先还是时间顺序优先？

取的是**种类为主序、时间为次序**：这样"按 CET-4 → CET-6 → … 排列"这条明确的、
可肉眼校验的要求一定成立；同种类内再按时间倒序（最近在前，
与课程成绩页学期 `sortedDescending()` 的既有约定一致）。

⚠️ 这是我做的判断，用户没确认过方向。若他更想要"整表按时间排"，只需
把 `gradeRowsSorted` 里 `compareBy` 与 `thenByDescending` 的主次换一下。
